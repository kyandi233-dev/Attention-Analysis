<a id="03-pytorch"></a>

## 03｜安装或验证 GPU 版 PyTorch

### 第一原则：已有成功环境时不要重装

如果这台电脑就是前次已经跑通过的 RTX 4060 机器，优先执行：

```cmd
conda activate D:\conda_envs\eye-ai
python -c "import torch; print(torch.__version__); print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else None)"
```

若得到类似：

```text
2.11.0+cu128
True
NVIDIA GeForce RTX 4060 Laptop GPU
```

就不要重新安装 PyTorch。

### 真正需要重建环境时

目标是安装 **CUDA 版 PyTorch**，不是 CPU-only wheel。前次最终可用版本是：

```text
torch 2.11.0+cu128
```

PyTorch 的具体下载命令会随官方发布变化，因此新装时应以 PyTorch 官方安装选择器给出的 CUDA 12.8（或当前与你驱动兼容的 CUDA wheel）命令为准。安装完成后必须用下一节的四项检查验证，而不是只看 `pip install` 是否成功。

### 不需要单独安装完整 CUDA Toolkit 才能让 PyTorch wheel 使用 GPU

对于常规 PyTorch pip/conda GPU wheel，关键是：

1. NVIDIA 驱动正确；
2. 安装的是 CUDA-enabled PyTorch；
3. `torch.cuda.is_available()` 为 True。

不要看到系统没有某个 `nvcc` 就直接判断 PyTorch GPU 不能工作。

<a id="05-opencv"></a>

## 05｜OpenCV contrib 与 `cv2` 冲突

这是前次环境配置中真正踩过的坑之一。

### 为什么会出问题

下面两个包都会提供同一个 Python 模块：

```text
opencv-python
opencv-contrib-python
```

它们都导入为：

```python
import cv2
```

如果两个版本在环境里混装、覆盖顺序异常，可能出现：

- `cv2` 能导入但 Tracker 不存在；
- `cv2.legacy` 不完整；
- 安装一个包后另一个包的二进制被覆盖；
- KCF/CSRT 创建函数报错。

### 当前 pipeline 正式模式是否还需要 tracker？

正式 `formal` 模式已经默认逐帧 YOLO，不依赖 KCF/CSRT；但旧诊断模式仍保留 tracker，所以环境仍推荐使用 contrib 版本。

### 正确检查

```cmd
python -c "import cv2; print(cv2.__version__); print('CSRT=', hasattr(cv2,'TrackerCSRT_create') or (hasattr(cv2,'legacy') and hasattr(cv2.legacy,'TrackerCSRT_create'))); print('KCF=', hasattr(cv2,'TrackerKCF_create') or (hasattr(cv2,'legacy') and hasattr(cv2.legacy,'TrackerKCF_create')))"
```

### 当前推荐

新建干净环境时优先安装：

```text
opencv-contrib-python >= 4.10
```

而不是同时安装两个 OpenCV wheel。

### 已经能正常运行时

不要仅因为 `pip list` 看见版本不够“漂亮”就卸载重装。先运行：

```cmd
python run_pipeline.py check-env
```

只有实际 `cv2` / tracker / import 出错时再处理。

### 如果已经混装并导致 `cv2` 损坏

这是修复动作，不是每台电脑都要执行。确认环境确实坏了以后，可以先查看：

```cmd
python -m pip list | findstr opencv
```

如果同时存在 `opencv-python` 和 `opencv-contrib-python`，再统一清理并只安装 contrib。不要在一台已经稳定工作的机器上盲目做这个动作。

<a id="07-ritnet"></a>

## 07｜RITnet 环境、预处理与历史问题

### 历史配置过程

前次从零配置时曾单独 clone RITnet 到：

```text
D:\NIR_Analysis\RITnet
```

并验证：

```python
from densenet import DenseNet2D
```

可以正常导入。

### 现在的新电脑是否还需要单独 clone RITnet？

**正常情况下不需要。**

当前 GitHub runtime 已经包含：

```text
runtime\nir-yolo-tracking-ritnet-v1\ritnet\densenet.py
runtime\nir-yolo-tracking-ritnet-v1\models\ritnet-best_model.pkl
```

所以现在推荐直接使用仓库里的 portable runtime；单独 clone `D:\NIR_Analysis\RITnet` 只属于历史排错过程，不是当前正式运行的必要步骤。

### 已确认的 RITnet 预处理

前次逐项核对过的输入预处理是：

```text
灰度
→ gamma = 0.8
→ CLAHE clipLimit = 1.5, tileGridSize = (8, 8)
→ normalize mean=0.5, std=0.5
```

当前 runtime 继续使用该逻辑。

### 历史 `best_model.pkl` / `torch.load` 问题

前次手工检查原始 RITnet `best_model.pkl` 时，确认它本质上是 `OrderedDict/state_dict`。在当时的手工加载实验里曾使用：

```python
torch.load(..., weights_only=False)
```

成功读取。

但当前 portable runtime 对仓库中已经确认的权重使用更严格的 `weights_only=True`。因此以后如果当前 runtime 出现加载错误，**不要第一反应就把代码永久改成 `weights_only=False`**。应先确认：

1. 当前分支是否正确；
2. 模型文件是否完整；
3. 是否下载了不同版本的 `best_model.pkl`；
4. `run_manifest.json` / GitHub 中记录的模型 SHA 是否一致。

`weights_only=False` 会允许 pickle 加载更广泛的 Python 对象，只应作为受信任历史模型的诊断手段，不应成为默认修复动作。

### 当前 RITnet 运行方式已经和旧版不同

旧版：

```text
单只眼 infer
→ GPU
→ .cpu().numpy()
→ 第二只眼再 infer
```

当前 formal：

```text
多只眼 ROI 累积
→ batch（默认16）
→ 一次 GPU forward
→ 批量回 CPU 后处理
```

这就是当前主要性能优化之一。

## 12｜批处理：用 YAML 指定跑哪些被试

文件：

```text
runtime\nir-yolo-tracking-ritnet-v1\config.yaml
```

当前关键配置：

```yaml
data:
  roots:
    - "F:/正式实验"
    - "E:/Data"

formal:
  min_subject_number: 31

batch:
  subjects:
    include: []
    exclude: []
  device: "0"
  continue_on_error: true
  skip_completed: true
  output_root: "outputs/formal"
```

### A. 跑所有被发现的 sub-031+

```yaml
include: []
exclude: []
```

### B. 只跑指定被试

```yaml
batch:
  subjects:
    include:
      - "sub-031"
      - "sub-033"
      - "sub-056"
    exclude: []
```

程序按 include 顺序执行。

### C. 跑全部，但排除几个人

```yaml
batch:
  subjects:
    include: []
    exclude:
      - "sub-056"
      - "sub-071"
```

### D. 临时指定，不修改 YAML

```cmd
python run_formal_batch.py --subjects sub-031,sub-033,sub-056
```

命令行 `--subjects` 会在这一次运行中覆盖 YAML 的 include。

### E. 先演练

```cmd
python run_formal_batch.py --dry-run
```

### F. 正式运行


<a id="13-performance"></a>

## 13｜FP32、FP16、batch size 与 GPU 性能

### FP 是什么

`FP = Floating Point`，即浮点数的数值表示格式。

- FP32：32-bit 浮点，精度更高，当前科研基准。
- FP16：16-bit 浮点，精度更低、显存更省，RTX GPU 通常更快。

CPU/GPU 是“谁负责计算”；FP32/FP16 是“计算数值用什么精度”，不是同一维度。

### 当前默认

```yaml
ritnet:
  batch_size: 16
  precision: fp32
```

也就是说，不写参数就是：

```text
RTX GPU + RITnet batch16 + FP32
```

### 测 FP16

```cmd
python run_pipeline.py formal --video "F:\正式实验\sub-033_\nir\sub-033_nir.avi" --ritnet-precision fp16
```

### 测 batch 32，但精度保持 FP32

```cmd
python run_pipeline.py formal --video "F:\正式实验\sub-033_\nir\sub-033_nir.avi" --ritnet-batch-size 32 --ritnet-precision fp32
```

### `batch=16` 和 `FP16` 不是一回事

```text
batch_size=16 = 一次送最多16个眼睛 ROI 给 RITnet
FP16          = 每个浮点计算主要采用16-bit格式
```

### 为什么当前不支持 CPU + FP16 formal

并不是 CPU 在物理上不能表示 FP16，而是这套 pipeline 的性能优化目标是 NVIDIA CUDA。CPU half precision 没有被我们做稳定性和速度验证，所以如果显式写：

```cmd
--device cpu --ritnet-precision fp16
```

程序应明确拒绝，而不是偷偷改成 FP32。科研运行必须让“请求参数”和“实际参数”一致。

### 历史速度数据为什么支持逐帧 YOLO

同一段 60 秒历史 benchmark：

```text
YOLO every frame / tracker none : 16.48 FPS
KCF r10                         : 10.48 FPS
CSRT r10                        :  3.78 FPS
```

所以当前 formal 默认每帧 YOLO，不再把 CPU KCF 当作提速手段。

## 14｜FocusWave v3.1.3 正式 phase 规则

正式实验版本必须以：

```text
FocusWave release v3.1.3
```

为准，而不是仓库某个后续开发分支的当前 HEAD。

当前分析保留：

```text
baseline
instructions
practice
block1
block2
```

### baseline

FocusWave 会先记录 `baseline_start`，但此时屏幕上还有“请确认是否调整好坐姿 / 即将开始静坐测试 / 按空格开始”的确认页。

真正静息时间固定：

```text
180 秒
```

因此 current formal 的 baseline 使用：

```text
baseline_stop - 180s → baseline_stop
```

而不是把整个 `baseline_start → baseline_stop` 都算作严格静息。

### instructions

`instructions` 是两张实验说明图片，从 timeline 的：

```text
instructions → practice_start
```

作为独立 phase 保存。

它不是严格静息，但可能是相对放松/低任务负荷状态，因此保留给后续基线比较，不和 180 秒 resting baseline 混在一起。

### practice

优先读取：

```text
beh\*Practice_run*.csv
```

使用其中 `absolute_onset_time` 定位真实练习 trial，尽量排除 321 倒计时和练习结束页。

### block1 / block2

使用 `master_timeline.csv` 中：

```text
block_start → block_stop
```

v3.1.3 是 BB 两个正式 block，各 432 trials。

### 默认排除

- 初始摄像头/坐姿调整；
- cover；
- Block1 与 Block2 中间强制休息；
- 休息后的 NIR 坐姿重新调整；
- 结算页；
- 实验结束后忘记及时结束造成的尾部空录。

### formal 必需的时间文件

```text
sub-XXX_\beh\master_timeline.csv
sub-XXX_\nir\sub-XXX_nir_timestamps.csv
```

如果 NIR timestamps 缺失，formal 应直接失败，不允许靠固定帧率猜 Unix 时间轴。

### `summary.json`

用于判断该被试正式 pipeline 是否完整结束，也是 batch runner 默认的“已完成”标记。

### `run_manifest.json`

用于保存真正生效的：

- command；
- FocusWave release；
- phases；
- tracker；
- yolo_every_frame；
- RITnet batch；
- RITnet precision；
- device；
- overlay stride；
- 模型 SHA256；
- CUDA 状态。

以后复现实验时应优先看 manifest，而不是只看当前 YAML，因为命令行参数可能覆盖 YAML。

### overlay

当前：

```yaml
output:
  overlay_stride: 3000
```

30 FPS 下大约每 100 秒一张，且每个 phase 会保留开头 QC 图。

历史旧版 `run` 是在整段视频结束后才集中写主 CSV；如果 Ctrl+C 中断正在处理的视频，该被试当前 CSV 可能丢失，而之前已经完成的被试不会受影响。

当前正式批处理仍建议：

- 尽量在一个被试结束后再停止；
- 通过 `summary.json` 判断是否完成；
- 重新运行时 `skip_completed: true` 会跳过完整结果。

<a id="17-history"></a>

## 17｜前次从零配置中已经遇到的问题、测试结果和最终结论

这一节用于记录“为什么现在这样配置”，避免以后把已验证结论重新推翻。

### 17.1 CUDA 不是没调用

前次 pipeline summary 明确记录 RITnet：

```text
cuda:0
```

YOLO 也通过 Ultralytics `device=0` 在 GPU 运行。

完整 pipeline 慢的原因不是“完全没用 GPU”，而是：

- YOLO：GPU；
- RITnet：GPU；
- 视频解码：CPU；
- OpenCV ROI：CPU；
- KCF/CSRT：CPU；
- `findContours/fitEllipse`：CPU；
- GPU→CPU 结果传输：存在同步开销；
- overlay JPEG：CPU + 磁盘。

因此后来才做了 RITnet batch 和去重 resize 优化。

### 17.2 历史 60 秒 benchmark

同一 1800 帧 / 60 秒段：

| 模式 | processing FPS | 结论 |
|---|---:|---|
| tracker none / 每帧 YOLO | 16.48 | 最快 |
| KCF r10 | 10.48 | 连续性较好，但更慢 |
| CSRT r10 | 3.78 | 明显过慢 |

所以 current formal 默认 tracker `none`。

### 17.3 历史 KCF 结果不能简单理解成“更准”

KCF 的双眼帧覆盖率提高，但 RITnet valid rate 没同步提高；因此 tracking 是 coverage / continuity trade-off，不是无条件提升质量。

### 17.4 `roi_clipped` 的语义曾经容易误读

`status=roi_clipped` 只表示：

```text
ROI碰边，但 RITnet 仍找到有效 pupil
```

同时也可能存在：

```text
roi_clipped = True
status = ritnet_missing
```

所以以后统计 clipping 必须看布尔 `roi_clipped` 字段，不能只数最终 `status == roi_clipped`。

### 17.5 `ritnet_missing` 不等于眨眼

历史帧检查发现闭眼/眯眼时确实可能 `ritnet_missing`，但 missing 还可能来自：

- 反光；
- 模糊；
- 遮挡；
- ROI问题；
- 分割失败。

所以不能直接把所有 `ritnet_missing` 当 blink。后续闭眼/眨眼需要独立 eyelid openness / closure 指标。

### 17.6 旧 RITnet 为什么慢

历史代码是左右眼各自调用一次：

```text
左眼 infer → GPU→CPU
右眼 infer → GPU→CPU
```

而且 ROI：

```text
原始crop → 320×160 → RITnet再放大640×400
```

current formal 已改为：

```text
raw crop → 直接640×400 → batch GPU → mask映射回320×160分析坐标
```

### 17.7 FP32 / FP16 当前决策

FP32 仍然是默认科研基准。FP16 只作为 RTX CUDA benchmark 候选；必须在同一视频上比较 pupil center、diameter、missing rate 后才能考虑改默认值。

### 17.8 正式实验协议曾看错分支

正确来源是：

```text
FocusWave release v3.1.3
```

不是 FocusWave 当前开发 HEAD。

v3.1.3 正式结构为两个 B block。sub-030 以前的三 block 数据当前暂时不用于本 formal pipeline。

### 17.9 baseline 时间不能直接用 baseline_start

`baseline_start` 在确认静坐页面出现之前记录，因此 strict resting baseline 必须用：

```text
baseline_stop - 180 秒 → baseline_stop
```

同时 `instructions` 独立保留，作为可能的低负荷/放松比较阶段。
