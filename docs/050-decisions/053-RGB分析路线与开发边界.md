# 053｜RGB 分析路线与开发边界

**Status: Proposed**

## 决策背景

NIR 正式分析已经完成并形成稳定 AMD/DirectML runtime；RGB 在 `rgb-dev` 上进行正式视频方法验证，不直接改动稳定 NIR 路线。RGB 目标是建立可与 NIR/Behavior 对齐的连续行为测量，而不是直接生成 Attention Score。

## 当前路线

1. **Motion**：OpenCV frame-difference global Motion 已在 `sub-031` 正式视频上完成 gap/QC/review 验证；
2. **Pose**：MediaPipe Tasks Pose Landmarker / Pose Lite / VIDEO mode，`sub-031` 10 fps 完整正式时间窗 pilot、landmark QC 和质量门控后的派生 feature 均已完成；
3. **Face**：已进入 Py-Feat Detectorv2 vs LibreFace 2.0 benchmark。

## 信息保留决策

RGB 强制遵循 `docs/040-rgb/044-RGB输出Schema与信息保留原则.md`：昂贵推理尽量只运行一次，raw 层优先保存以后难以恢复的完整模型输出；QC 先 flag 后 filter；derived feature 与 summary 尽量从 raw 重建；正式结果通过 manifest 记录模型、配置、版本、hash、Git commit 和源文件 provenance。

## Pose 当前结论

`sub-031` Pose 10 fps representative pilot：15,494 个采样时点，`pose_valid_fraction=1.0`，0 multi-pose frame，约 429.1 s / 7.15 min，实际约 36.1 inference/s，输出约 22.7 MB。

逐 landmark QC 显示：nose 与双肩稳定且始终入画；肘、腕、髋大多为画外模型外推。`rgb-pose-features-v0.2` 经 visibility/presence/in-frame 质量门控及 >300 ms gap reset 后，shoulder motion 有效 15,491 行、elbow 0 行、wrist 6 行、trunk angle 0 行。因此当前 Pose 正式解释优先收敛到 shoulder motion / shoulder center / shoulder-line posture；其他部位仅在各被试实际质量通过时作为 opportunistic 指标。

`body_motion_energy` 是人体 ROI 内的像素级帧差，不等同于 Pose-derived motion；它等待 Face backend 冻结后与正式统一视频读取一起实现，避免当前重复扫描大体积 AVI。

## Face benchmark 共同输入决策

第一轮 Face 工具筛选不让两个候选各自先跑完整正式长视频，也不允许各自独立抽帧。新增 `face-sample`：从同一 `sub-031` 正式分析时间窗按 phase 均匀、确定性地提取 **350 张共同 JPEG**，并保留原 `video_frame_position`、`capture_frame_idx`、Unix timestamp、phase/block 与行为上下文。

```powershell
python scripts/rgb_analysis.py --stage face-sample --subject sub-031
```

共同样本固定为 baseline 50、instructions 25、practice 35、transition 15、block1 90、interblock transition 45、block2 90。该样本只用于第一轮 candidate screening，不代表最终 Face inference fps。

Py-Feat 和 LibreFace 必须使用这同一 frame manifest。第一轮比较：安装/初始化稳定性、face coverage、原生输出完整性、缺失/多人语义、350-frame CPU wall time，以及后续 AMD/DirectML 移植成本。只有候选胜出后才投入连续时间窗稳定性和最终 fps 冻结。

Face benchmark raw 层不提前做 common-AU 交集筛选。Py-Feat Detectorv2 原生多任务输出尽量全保留；LibreFace 的 AU detection、AU intensity、expression、gaze、head pose/landmark 等组件也分别保留后再生成 convenience merge。

## AMD / backend 边界

MediaPipe Python Pose 当前使用 CPU/XNNPACK，实测速度可接受，因此不为 Pose 单独增加 DirectML 工程。Face 第一轮同样先使用各候选官方 CPU reference backend，避免一开始把科学模型比较和自定义部署移植混在一起。

如果胜出候选 CPU 全量速度不可接受，再评估 ONNX Runtime DirectML。LibreFace 2.0 已公开 ONNX derivative 路线，因此在 AMD 部署成本上具有潜在优势；Py-Feat Detectorv2 若需要 DirectML，则必须另外验证完整 preprocessing/postprocessing 和数值一致性。
