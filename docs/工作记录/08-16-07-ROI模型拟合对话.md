DeepVOG/RITnet/pye3d 这一层解决的是"给定一个已经框出来的单眼图，做瞳孔/虹膜提取"，跟 PuRe/PuReST 是同一层的替代品，不解决"双眼特写画面里眼睛到底在哪"这个上游问题。这个订正很关键，我重新说。

## 先确认一件事

你的目录文档里写的是 sub‑011 Block1 这次 60 时点复核 MediaPipe 0/60——如果这个 0/60 在你其他 subject/block 上也是普遍情况（毕竟设备装置固定、拍摄几何应该是一致的），那"MediaPipe 优先、眼部专用 ROI 补检测不到的帧"这个思路在逻辑上就有问题：**没有"优先"的基础，因为它基本从来不成功**，也就没有"剩下的帧"这个说法，需要补的其实是全部。

如果确实是全局性的 0%，我建议直接把优先级反过来：**眼部专用检测器做主力，MediaPipe（或人工标定）只在极少数场景下当"锚点"用**。如果你有别的 subject/session 里 MediaPipe 确实偶尔能成功（比如头往后仰一点、露出了更多脸部上下文），那可以做成"能检出就用，检不出就退到追踪"的混合策略——但这个前提需要你确认一下实际情况，因为这决定了架构怎么搭。

## 这层问题本身没有现成的开源方案

我查了一下，"不依赖完整人脸、只在部分可见（甚至只有双眼+鼻梁）的近红外画面里定位眼睛"这件事，在文献里是个专门被研究、但一直没有成熟开源方案的窄问题：

- 一篇周期性文献综述明确指出，相比人脸检测领域几十年的积累，能在没有鼻子到下巴区域支持的情况下直接定位眼睛的方法非常少，而主流深度学习人脸检测器都是按检测整张脸设计的，训练数据里虽然包含遮挡样本，但并没有专门针对"只有眼周区域可见"这种情况去训练或评估。这跟你测出来的 MediaPipe/YuNet/YOLO‑face 全灭的结果是一致的，不是你的设备或调参问题。
- 更贴近你场景的是 NEC 2023 年那篇 专门针对近红外部分人脸图像（不含完整人脸，因为是虹膜识别设备在受帧率/分辨率约束下采集的）设计的快速眼部检测方法，用 Siamese 网络做粗到精的位置估计，专门解决左右眼判别和眼中心定位——这跟 Causa 论文里的 Eye‑tiny‑yolo 是同一类问题、同一类解法（都是"为这个具体输入域训练一个轻量专用检测器"），而且这篇同样**没有开源代码/权重**。

结论是：这一层不存在"下载一个现成模型直接用"的路，工业界和学术界处理它的通用做法都是**自己针对具体采集设备训练一个轻量专用检测器**，不是通用人脸检测器的调参问题。

## 建议的架构

1. **主力：自训练轻量眼部检测器**——不用人脸 landmark，直接对整帧做"左眼框/右眼框"检测（YOLOv8n-tiny 这类小模型即可，2类或单类跑两次）。因为你的相机固定安装、距离固定在 30cm、拍摄几何基本一致，标注成本不高——几百帧、覆盖不同 subject 和头部姿态范围，大概率就够训一个在你这个域内相当稳的检测器。这本质上是在复刻 Eye‑tiny‑yolo 的设计思路，只是用你自己的数据。
2. **检测+追踪，而不是逐帧检测**——参考 Causa 论文自己的做法（Eye‑tiny‑yolo 检测 + MIL/CSRT 追踪 + 精修），也是这类系统的常见工程模式：每个目标只在首次出现的帧上做一次检测，后续帧用成熟的视频追踪方法持续跟踪，比逐帧跑检测器更省算力也更稳（追踪对遮挡、瞬时反光的鲁棒性通常比单帧检测好）。具体可以用 OpenCV 自带的 CSRT/KLT 光流，检测器定期（或追踪置信度掉下去时）重新锚定一次。
3. **人工标定兜底**——如果你的实验里头动范围本来就小（受试者坐姿固定做 SART 任务），甚至可以给每个 session 开头人工标一次双眼框，后面全靠追踪撑住，检测器只用来做异常恢复（比如追踪丢失、大幅度晃头之后重新找回）。
4. **拿到干净的单眼裁剪之后**，再进入瞳孔/虹膜这一层——这时候 DeepVOG / RITnet / PuRe‑PuReST 才是我上一轮说的那个位置，互相是候选替代品。

如果你确认 MediaPipe 在你其他数据上也基本是全局失效，我可以帮你把标注（工具选型、标注量级估算）和 YOLOv8n 微调+CSRT 追踪这条流水线的具体实现方案再往下细化。

## 0. 先定一个关键设计决策：输出关键点，不是纯 bbox

看你 `roi_mediapipe.py` 的代码，下游 `normalized_eye_roi()` 是靠 `EYE_CORNERS` 这几个眼角关键点做相似变换（旋转+缩放+平移）裁出 320×160 的标准化 ROI，`roi_payload()` 也要吃 `canthi_source` 点。如果新检测器只出 bbox，你还得重新设计裁剪/配准逻辑。

所以正确的替换粒度应该是：**只换掉"怎么拿到眼角关键点"这一步，其余（`roi_common.py`、EAR 计算、序列 CSV 输出）全部不动。** 也就是训练一个轻量的**关键点检测模型**（pose/landmark 任务），直接输出跟 MediaPipe 原来给你的那几个眼角点语义一致的坐标，而不是训练一个纯目标检测（bbox）模型。这是能最快接回现有管线的做法。

另外建议：不要分"左眼类/右眼类"两个 class，用单一 "eye" class，每帧检出两个实例，靠 x 坐标排序区分左右（画面里 x 更小的是受试者右眼，因为是正对拍摄）。这样标注更简单。如果以后发现头部有明显 roll（侧倾）导致排序不稳，再拆成两个 class 也不迟——NEC 那篇论文之所以要专门做左右眼判别，是因为他们的场景头部姿态变化范围更大；而在没有鼻子到下巴区域支持的窄视场里做左右眼判别本身就是这类系统要专门处理的难点之一，你的实验受试者是固定坐姿，先按简单方案走，有问题再升级。

## 1. 准备清单

**软件环境**（装在你的主环境 `D:/Code/python/python.exe`）：

```powershell
pip install ultralytics labelme
```

- `ultralytics`：训练框架，同时支持 detect 和 pose(关键点) 任务，CLI 和 Python API 都很简单。当前默认模型是 YOLO26（`yolo26n-pose.pt`），Ultralytics 官方明确支持用自定义关键点集合训练——关键点数量和骨架结构由你自己的数据集定义，标注、配置关键点数量和骨架，然后直接训练即可，YOLO11 系列同 API 也仍受支持，两者都行。
- `labelme`：本地标注工具，纯离线、无需联网/上传，GUI 点几下就能标 bbox 和关键点，导出 JSON。**不建议用 Roboflow 这类云端标注平台**——你的数据是可识别的人体生物特征影像（眼部+受试者身份相关），涉及伦理审查的话上传到第三方云服务大概率不合规，本地工具更稳妥。如果以后需要多人协作标注，可以自建 CVAT（Docker 自托管，不经过外部服务器）。

**硬件**：有 GPU 更快，但 nano 级模型 + 几百张图的数据量，CPU 也能在可接受时间内跑完（离线分析场景，你本来就不追求实时）。

**数据来源**：你现在应该已经有 sub‑011 等 pilot 的原始 NIR 视频，从这些视频里抽帧即可，不需要额外采集。

## 2. 抽帧策略

避免标连续帧——30fps 下相邻帧几乎一样，标了也白标。建议：

- 按时间间隔抽（比如每 1～2 秒一帧，即每 30～60 帧取一张），在每个已有 session/block 里均匀撒开
- **刻意补充边界样本**：眨眼/闭眼帧、头动幅度较大的帧、眼镜反光明显的帧——这些正是你之前诊断出的失败模式，训练集里没有就学不会
- 起始目标：**300～500 帧**，尽量覆盖你现有的所有 pilot 受试者/session（哪怕每人 subject 只贡献几十帧也比单一 subject 刷满 500 帧更有价值，因为你要的是跨受试者泛化）
- 不用死磕一次到位，第 9 步会讲怎么迭代补数据

## 3. 标注规范

用 `labelme` 打开图，对每只眼睛标：

1. 一个矩形框（bbox）：眼睛区域外扩一点余量，别卡得太紧
2. 两个关键点：**内眼角、外眼角**（跟你 `roi.py` 里 `EYE_CORNERS` 用的语义必须一致——标注前先去确认一下 `EYE_CORNERS` 具体对应的是哪两个角点、顺序是什么，标注顺序要跟它对齐，否则训完的模型输出接不上现有的仿射变换代码）

写一份简短的标注口径说明（比如"点标在上下眼睑交界处"），标注一致性比像素级精度更重要——模型学的是你标注的分布，标注本身漂移，模型也会跟着漂移。

## 4. 数据集划分

80/20 或 85/15，**按 subject/session 切分，不要按帧随机切分**——同一个人连续帧高度相关，随机切分会让验证集"泄漏"，虚高你的验证指标，掩盖真实的跨受试者泛化能力（你最终要在 N=500 个新受试者上跑，训练时没见过的人才是真正的考验）。

## 5. 格式转换

`labelme` 的 JSON 转成 YOLO‑pose 需要的 txt 格式，每行：

```
class  x_center y_center width height  kpt1_x kpt1_y kpt1_v  kpt2_x kpt2_y kpt2_v
```

全部是相对图像宽高归一化到 0~1 的坐标，`v` 是可见性标志（0=未标注，1=标注但不可见，2=标注且可见）。写个几十行的转换脚本就够了（遍历 JSON，取 rectangle 和两个 point，按图像宽高归一化）。

配套 `data.yaml`（具体字段名建议对照你安装的 ultralytics 版本文档核实一下，这块偶尔会有语法微调）：

```yaml
path: ./eye_dataset
train: images/train
val: images/val
names:
  0: eye
kpt_shape: [2, 3]   # 2个关键点，每个(x, y, visibility)
```

## 6. 训练配置——两个容易踩的坑

```powershell
yolo pose train `
  data=eye_dataset.yaml `
  model=yolo26n-pose.pt `
  imgsz=960 `
  epochs=200 `
  batch=16 `
  fliplr=0.0 `
  hsv_h=0.0 hsv_s=0.0 `
  patience=30 `
  project=runs_eye_kp name=v1
```

- **`fliplr=0.0` 必须关**：YOLO 默认会做水平翻转增强，你的场景是固定装置正面拍摄，翻转后左右眼位置语义会错乱（原本 x 更小的是右眼，翻转后变成左眼），不关掉的话相当于往训练集里注入错误标签。
- **`hsv_h=0.0 hsv_s=0.0` 建议关**：默认的色调/饱和度增强对灰度 NIR 图像没有意义，纯粹是浪费训练容量甚至引入噪声。
- `imgsz`：先从 960 试起，你的原始帧是 1920×1080，眼部区域在整帧里占比不算大，如果实测发现小图丢细节可以往上调（1280），跟推理速度做权衡（反正你是离线批处理，不需要实时，可以偏保守往大调）。
- `epochs=200 + patience=30`：小数据集用 nano 模型这个量级通常够，早停避免过拟合。

## 7. 验证——跟你已有的口径对齐

不要只看 mAP/PCK 这类抽象指标，直接复用你之前对比 MediaPipe/YuNet/YOLO‑face 的**同一套 60 时点复核方法**（定位阳性/正确双眼 ROI），跑一遍新模型，产出跟你现有那张表同构的一行，这样才是苹果对苹果的对比，也方便你判断"这个方案到底行不行"而不是被一个抽象数字误导。

## 8. 接回现有管线

按 `roi_mediapipe.py` 的接口模式，新写一个 `roi_custom.py`（或你喜欢的命名），照抄 `MediaPipeRoi` 类的结构：一个 `.eyes(frame)` 方法返回 `{eye: payload}` 字典，`.close()` 收尾，用 `roi_common.add_common_args`/`resolve_common_args`/`finish` 接现有的 CLI 和输出管线。内部把 `FaceLandmarkerSession.detect()` 换成你训练好的 YOLO‑pose 模型推理，取到关键点后依然调用 `normalized_eye_roi()` 和 `roi_common.roi_payload()`——这两步完全不用改。这样新模型是**平级替换候选**，跟 `roi_mediapipe.py`/`roi_yunet.py`/`roi_yolo.py` 走同一套评测和汇总逻辑，直接能塞进 `run_roi_selection.py` 的候选列表里。

模型推理放在你的主环境（不是 pupil venv），跟你现有的双环境划分保持一致。

## 9. 别想着一次做完——用迭代闭环

初始 300～500 帧训出一版可用模型后：拿它去跑更多原始视频 → 人工过一遍找出它检测失败/明显偏移的帧 → 把这些帧修正标注后加回训练集 → 重训。这种主动学习式的迭代，比一开始就死磕标 2000 帧然后训一版，效率通常高得多，也更容易把力气花在真正的失败模式上（比如反光、大幅度眨眼过程中的中间态）。
