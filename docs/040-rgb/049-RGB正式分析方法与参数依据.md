# 049｜RGB 正式分析方法与参数依据

> 文档定位：本文件记录 RGB 正式分析的**方法学逻辑、算法结构、跨硬件实现、参数选择依据与可回溯性原则**，可作为研究报告/论文“方法”部分的技术底稿。运行命令、环境搭建和历史 benchmark 分别见本目录其他文档。
>
> 当前正式主线：**Face + Pose + Motion**。分析时间范围为 **baseline 开始连续至 Block2 结束**，包括 instructions、practice、transition、inter-block transition 等中间阶段；所有模态通过真实时间戳与行为数据对齐。

---

## 1. 总体分析目标与设计原则

本研究使用实验过程中同步采集的 RGB 视频，对被试的面部活动、眼睑状态、头部姿态、身体姿态及整体运动变化进行非接触式量化。RGB 分析并不在模型推理阶段直接生成最终心理学指标，而采用 **raw-first（原始模型输出优先）** 的数据策略：首先完整保存计算代价较高、后续无法在不重新运行模型的情况下恢复的信息，再在下游根据具体研究问题构建 tracking、EAR、眨眼、PERCLOS、姿态变化、运动量以及 trial/probe 时间窗统计。

该策略遵循三个原则：

1. **昂贵推理尽量只执行一次。** Face 与 Pose 模型首次推理时尽可能保存其可用原始输出；
2. **筛选晚于测量。** 多脸、no-face、低质量 landmark、时间戳 gap 等首先保留并标记，不在 raw 层静默删除；
3. **科学参数与工程参数分离。** 采样频率、模型版本、检测阈值等影响测量定义的参数固定；batch、prefetch、运行设备等仅影响计算效率的参数允许按硬件优化。

> 原始 RGB AVI + timestamps + master timeline + Behavior → Face / Pose / Motion 三支 → raw parquet → downstream derived → trial/block/probe 统计。

## 2. 正式分析时间范围与时间对齐

### 2.1 分析区间

正式区间定义为：

```text
baseline start
→ instructions / practice / transition
→ Block1
→ inter-block transition
→ Block2
→ Block2 end
```

当前 FocusWave 正式版本（v3.1.3 / v3.1.4，BB 结构）baseline 固定为 180 s，因此代码使用：

```text
analysis_start = baseline_stop - 180 s
analysis_end   = last_formal_block_stop
```

中间阶段不删除，以保留实验状态变化、主试进入/离开画面、任务切换及恢复阶段等信息。

### 2.2 三种帧身份必须区分

RGB 数据同时保留：

- `video_frame_position`：该图像在 AVI 文件中的顺序位置；
- `capture_frame_idx`：采集端记录的原始帧编号；
- `unix_ms`：该帧的绝对 Unix 时间戳。

这一设计用于处理采集帧编号跳号、timestamp gap 等情况。后续任何跨模态分析均以 `unix_ms` 为主时间轴，同时保留 AVI 位置用于回查原视频画面。

### 2.3 行为上下文

Face、Pose 与 Motion 输出均可关联：

- trial 编号、条件、cycle、Go/No-Go 属性；
- response、correct、commission、omission；
- `trial_onset_unix_ms` 与 `time_from_trial_onset_ms`；
- probe onset / response；
- `trial_active`、`probe_active` 与 `behavior_state`。

因此可以在不重新读取实验脚本的情况下重建 block-level、trial-level、probe-centered window 和连续滑窗分析。

## 3. Face：Py-Feat 面部多任务分析

### 3.1 统一科学核心

两套硬件均以 **Py-Feat 2.1.1 Detectorv2 scientific core** 作为 Face 测量定义。Py-Feat Detectorv2 是多任务面部分析框架，可输出面部动作单元（Action Units, AU）、情绪类别、valence/arousal、gaze、头部姿态、面部关键点/FaceMesh 与 blendshape 等信息。正式分析关闭身份识别分支（`identity_model=None`），因为身份 embedding 不属于本研究科学变量。

正式 Face raw 主要保留：

- 所有检测到的人脸及 FaceScore；
- RetinaFace bbox 与 5-point landmarks；
- 20 个 AU；
- 7 类 emotion；
- valence / arousal；
- gaze；
- 6DoF head pose；
- 478-point 3D FaceMesh（归一化坐标与回投原图像素坐标）；
- 68-point compatibility landmarks；
- native blendshapes，包括 `eyeBlinkLeft` / `eyeBlinkRight`；
- multi-face rows 与 no-face planned sample placeholder；
- 完整帧身份、时间戳、phase 与行为上下文。

### 3.2 AMD：ONNX Runtime + DirectML 实现

Windows AMD GPU 无法使用 PyTorch CUDA，因此 AMD 工作线采用 **Py-Feat 模型的 DirectML port**，并非更换另一套 Face detector。执行结构为：

```text
RGB frame
  ↓
Py-Feat RetinaFace R34（ONNX）
  ↓
score threshold / bbox decode / 5-point landmark decode / NMS
  ↓
square face crop + Py-Feat preprocessing
  ↓
Py-Feat Detectorv2 multitask scientific core（ONNX）
  ↓
AU / emotion / VA / gaze / head pose / 478 mesh / blendshape
  ↓
formal Face raw parquet
```

ONNX Runtime 使用 `DmlExecutionProvider`。当前正式/benchmark 配置为：

| 参数 | 当前值 | 属性 |
|---|---:|---|
| Face sampling | 15 Hz | 科学参数 |
| detection threshold | 0.5 | 科学/检测规则 |
| NMS threshold | 0.4 | AMD detector 后处理规则 |
| RetinaFace batch | 32 | 运行参数，可按显存/吞吐调整 |
| multitask batch | 64 | 运行参数，可按显存/吞吐调整 |
| prefetch batches | 3 | 运行参数 |
| CPU postprocess inflight | 2 | 运行参数 |

AMD 优化版在 RetinaFace 输出后先筛除 `<0.5` 的候选，再对最终可能保留的候选执行 bbox / landmark decode 与 NMS。由于 NMS 按分数从高到低贪心处理，低于最终阈值的候选不能反向抑制更高分候选，因此该改动属于**计算顺序优化**，不改变最终 `score >= 0.5` 的保留规则。

同时使用 reader prefetch 与 CPU/GPU overlap，使视频解码、RetinaFace GPU 推理及 CPU decode/NMS/crop 尽量并行。上述 batch/prefetch/overlap 参数只改变计算分块和资源利用，不作为被试间科学条件。

### 3.3 NVIDIA：native PyTorch CUDA 实现

NVIDIA 工作线直接调用 Py-Feat 2.1.1 原生 `Detectorv2`：

```python
from feat import Detectorv2

detector = Detectorv2(device="cuda", identity_model=None)

fex = detector.detect(
    batch,
    data_type="tensor",
    batch_size=len(batch),
    num_workers=0,
    pin_memory=False,
    face_detection_threshold=0.5,
    progress_bar=False,
)
```

正式 runner 强制检查 `torch.cuda.is_available()`，不允许静默退回 CPU。与 AMD 不同，native Detectorv2 对外只暴露**一个端到端 batch**，因此不能把 AMD 的 RetinaFace B32 / multitask B64 机械翻译成 NVIDIA 的两个 batch。

当前 NVIDIA 默认 `native_cuda_batch=16`，并预留 16 / 32 / 64 作为 RTX 5070 的吞吐/显存 benchmark 候选。最终 batch 按实机吞吐冻结；batch 属于运行参数，不改变 Face 采样频率、模型版本、检测阈值和科学输出定义。

### 3.4 AMD 与 NVIDIA 的可比性原则

两端要求保持同一 scientific contract：

- Py-Feat 2.1.1 scientific core；
- Face sampling = 15 Hz；
- detection threshold = 0.5；
- identity branch 关闭；
- 所有检测人脸与 no-face 时点保留；
- 相同变量语义与统一时间身份。

但两端底层 runtime 不完全相同：AMD 为 ONNX Runtime DirectML 与自定义 glue code，NVIDIA 为 native PyTorch CUDA。因此正式跨平台合并前应使用一套**完全相同的代表帧 fixture** 做 backend parity，包括检测一致率、bbox IoU、AU、emotion、gaze、head pose、mesh 与 blendshape 的数值差异。这里验证的是“不同计算后端是否实现了同一测量”，而不是要求底层代码逐行相同。

## 4. Face 采样频率：为什么选择 15 Hz

Face 模块既要分析 AU、gaze、head pose 等相对连续信号，也要为后续眨眼和眼睑闭合提供时间序列。与身体姿态相比，眨眼和眼睑开闭是更短暂的事件，因此 Face 采用高于 Pose 的采样频率。

15 Hz 对应约：

```text
66.7 ms / sample
```

这一分辨率并不用于精确估计毫秒级眼睑运动学，而是为以下研究变量提供足够连续的采样：

- EAR / eye openness；
- blink occurrence 与 blink rate；
- 近似 blink duration；
- 持续或缓慢眼睑闭合；
- PERCLOS；
- probe 前后短时间窗的眼睑状态变化。

如果 Face 降到 10 Hz，每个时点间隔约 100 ms，较短 blink 可能仅留下 1 个低开度采样点，不利于事件识别；如果提升至原视频约 30 Hz，模型推理量近似翻倍，而本研究并不研究高速眼睑生物力学。因此 15 Hz 是**短时眼睑事件保留能力与大规模视频推理成本之间的折中**。

需要在报告中明确：**15 Hz 支持注意/警觉相关 blink 与 PERCLOS 分析，但不声称恢复精细 blink kinematics。**

## 5. Pose：MediaPipe Pose Landmarker

### 5.1 算法

身体姿态使用 MediaPipe Tasks Pose Landmarker（Lite），VIDEO 模式。MediaPipe/BlazePose 系列使用人体检测与姿态 landmark 模型，输出 33 个身体关键点。

正式配置：

| 参数 | 当前值 |
|---|---:|
| model variant | Lite |
| sampling | 10 Hz |
| maximum poses | 2 |
| min pose detection confidence | 0.5 |
| min pose presence confidence | 0.5 |
| min tracking confidence | 0.5 |
| segmentation mask | false |

Raw 层保存每个返回 pose 的 33 个 normalized coordinates、world coordinates、visibility、presence 与 pose bbox；多 pose 不提前删除；no-pose 时点保留 placeholder。

### 5.2 为什么选择 10 Hz

Pose 的主要目标不是高速运动学，而是持续 SART 坐姿条件下的：

- shoulder center / shoulder-line movement；
- 头肩姿态稳定性；
- 躯干/身体较慢调整；
- 可见情况下的肘、腕等运动。

10 Hz 对应约 100 ms 时间分辨率，对坐姿姿态和肩部变化已经较密。项目 pilot 中，`sub-031` 以 10 Hz 覆盖完整正式区间，共 15,494 个 Pose 时点，推理约 7.15 min，Pose frame coverage 为 100%，证明该采样率在当前机位和计算预算下具有可行性。

进一步 landmark QC 显示当前正式机位最稳定的是 nose 与双肩；肘、腕、髋经常位于画外，因此当前 Pose 的主要可靠研究价值是**头肩/肩部姿态和运动**，而不是完整全身骨架高速运动。将 Pose 从 10 Hz 提升到 30 Hz 会显著增加推理与存储量，但对当前最可靠的慢变化肩部指标增加的信息有限。

Pose derived 阶段才使用 visibility / presence / in-frame 等质量门控；raw 层不因 landmark 暂时不可见而删除数据。

## 6. Motion：OpenCV 全帧帧差

### 6.1 算法定义

Motion 分支不使用高成本深度模型，而对原始 RGB 视频的连续帧进行灰度帧差。设当前帧和前一帧灰度图分别为 \(I_t\) 与 \(I_{t-1}\)，则：

\[
D_t = |I_t - I_{t-1}|
\]

\[
GlobalMotion_t = \frac{\operatorname{mean}(D_t)}{255}
\]

同时根据真实时间差 \(\Delta t\) 可得到单位时间运动变化：

\[
GlobalMotionRate_t = \frac{GlobalMotion_t}{\Delta t_{sec}}
\]

当前还保存亮度统计、changed-pixel ratio、capture/timestamp gap 与真实 `dt_ms`。`pixel_diff_threshold=15` 用于定义显著像素变化比例。

### 6.2 为什么 Motion 使用原视频 full FPS

当前视频名义帧率约 30 fps，但正式规则不是固定“30 Hz”，而是：

```text
process_full_fps = true
```

即 Motion 跟随原视频的实际时间分辨率。原因在于**相邻帧差本身就是测量对象**。若将约 30 fps 降至 10 fps，原本约 33 ms 的相邻变化会变成约 100 ms 间隔的变化，指标的物理含义已经改变，而不是单纯少算两帧。

Motion 计算成本远低于 Face/Pose，因此没有必要为节省少量计算而主动丢弃原始运动时间结构。

遇到 timestamp/capture gap 时，不跨异常间隔计算相邻帧运动；gap 后第一帧仍保留身份信息，但相关 frame-difference 指标置为 missing，避免把采集断流误判为大幅身体运动。

需要注意，`global_motion_energy` 反映**整个画面**的像素变化，可能包含主试进入画面、背景变化等，并不自动等价于被试自身身体运动。人体 ROI motion / body motion 等指标应在 downstream 层结合 Pose/Face/QC 后谨慎定义。

## 7. 30 / 15 / 10 的统一参数逻辑

三个分支的频率不是按模型性能随意选择，而是依据**目标信号的时间尺度 + 信息不可恢复性 + 计算成本**确定：

| 模块 | 正式时间分辨率 | 目标信号 | 选择逻辑 |
|---|---:|---|---|
| Motion | 原视频 full FPS（当前约 30 fps） | 相邻像素变化 | 帧差定义依赖真正相邻帧；计算便宜，因此不降采样 |
| Face | 15 Hz | AU、gaze、head pose、EAR、blink、PERCLOS | 眼睑事件较短，需要高于 Pose 的时间分辨率；30 Hz 成本约翻倍，15 Hz 为科学需求与推理成本折中 |
| Pose | 10 Hz | shoulder/posture/body adjustment | 坐姿姿态变化较慢；pilot 已验证覆盖与吞吐，当前主要可靠点为头肩 |

因此这里的核心不是“30 比 15 好、15 比 10 好”，而是不同模态的**目标动态带宽不同**。正式报告应避免把采样频率解释成模型准确率参数。

## 8. 眼睑、EAR、Blink 与 PERCLOS 的下游重建

### 8.1 EAR

Face raw 已保存 478-point mesh，因此眼睛纵横比（Eye Aspect Ratio, EAR）可以在不重跑 Face 模型的情况下后算。基本形式为：

\[
EAR = \frac{\|p_2-p_6\| + \|p_3-p_5\|}{2\|p_1-p_4\|}
\]

EAR 用垂直眼睑距离与水平眼宽的比值描述眼睛开放程度，可降低整体人脸尺度变化的影响。

### 8.2 眼睑开度 / 虹膜直径标准化

除 EAR 外，当前 raw 包含 iris ring 与眼睑 mesh，因此可以构建：

- `eye_aperture_px_left/right`；
- `iris_diameter_px_left/right`；
- `aperture_iris_left/right`；
- normalized eye openness；
- closure fraction。

当前开发方案使用 baseline 中有效 aperture/iris 值的 top 30% 中位数作为个体开放参考；若 baseline 有效样本不足，则退回全程有效样本。该方法用于降低个体眼裂大小、脸距和相机尺度差异。

### 8.3 Blink

Blink 不是在 raw extraction 中提前二值化，而是保留两类证据：

1. 几何序列：EAR、aperture/iris、openness；
2. Py-Feat native blendshape：`eyeBlinkLeft` / `eyeBlinkRight`。

最终 blink event threshold、最短持续时间和双眼融合规则在代表被试分布与视频 overlay QC 后冻结，从而避免把一个尚未验证的阈值永久写进 raw。

### 8.4 PERCLOS

PERCLOS 通常定义为给定时间窗内眼睛达到高度闭合状态所占的时间比例，经典 P80 定义常以“眼睛至少闭合 80%（即开放度 ≤20%）”为判据。当前配置保留 `closure80_proxy` 与 60 s 窗口作为候选实现，但**最终统计定义仍属于 downstream QC/冻结环节**。

之所以 raw-first 后仍可调整 PERCLOS，是因为 15 Hz 时间戳、478 mesh、iris/eyelid geometry 与 native blink 信号均已落盘。未来若需要比较 70%、75%、80% 等阈值，或决定是否排除快速 blink，只需重算 derived 指标，无需重新跑 Py-Feat。

## 9. 参数分级：哪些能调，哪些不能随便调

### 9.1 科学/测量参数

这些参数会改变采样或测量定义，正式全量期间不应为了提速按被试调整：

| 参数 | 当前规则 |
|---|---|
| analysis span | baseline start → Block2 end，连续保留 |
| Face model | Py-Feat 2.1.1 Detectorv2 scientific core |
| Face sampling | 15 Hz |
| Face detection threshold | 0.5 |
| Identity | disabled |
| Pose model | MediaPipe Pose Landmarker Lite |
| Pose sampling | 10 Hz |
| Pose detection/presence/tracking confidence | 0.5 / 0.5 / 0.5 |
| Motion sampling | source-video full FPS |
| Motion definition | adjacent grayscale absolute difference |
| Motion changed-pixel threshold | 15 gray levels |
| Raw retention | all detected faces/poses + no-detection placeholders + timestamps/gaps |

### 9.2 运行/性能参数

这些参数原则上只影响吞吐、显存和调度，可按硬件 benchmark：

- AMD RetinaFace batch；
- AMD multitask batch；
- NVIDIA native CUDA batch；
- prefetch queue depth；
- CPU postprocess inflight；
- CUDA device index；
- worker / logging frequency。

这些参数改变的是“一次送多少样本给同一个模型”，不是“分析哪些帧或采用什么科学阈值”。正式冻结前仍应做数值稳定性与无 OOM 验证。

### 9.3 下游待冻结参数

以下参数可以从 raw 重建，目前不作为 extraction complete 的必要条件：

- face tracking 与 primary-face 选择；
- EAR / aperture-iris 的 QC 规则；
- blink event threshold 与 duration rule；
- PERCLOS 精确闭合阈值及是否排除快速 blink；
- Pose derived landmark quality gates；
- trial/probe/window 聚合长度；
- 最终被试级 QC inclusion criteria。

## 10. Raw 完整性与后续可回溯范围

完成一次正式抽取后，理论上无需重新运行昂贵模型即可重建：

- Face tracking / primary face；
- EAR、眼睑开度、虹膜标准化；
- blink rate、blink duration（受 15 Hz 时间分辨率限制）；
- PERCLOS；
- AU / emotion / VA / gaze / head-pose 时序统计；
- Pose shoulder/body posture motion；
- trial、block、probe-centered 和 sliding-window 特征；
- baseline normalization 与个体内标准化；
- capture/timestamp gap QC。

需要重新读取/运行原视频的情况主要包括：

1. 未来要求 Face 超过 15 Hz 或 Pose 超过 10 Hz 的**新模型推理**；
2. 引入当前 raw 中不存在、且必须依赖原始像素的新视觉模型；
3. 需要严格像素级 ROI motion，而现有 raw 没有保存对应像素图时。

因此当前 raw-first 设计的目标不是“保存所有可能的图像信息”，而是保存**当前已采用模型能够产生的、后续分析最可能需要且无法从低维派生结果恢复的信息**。

## 11. Extraction complete 与 QC pass 分离

正式 validator 的 `extraction_complete=true` 只表示：

```text
Motion raw 完整
+ Pose landmark raw 完整
+ Face raw 完整
+ 帧身份/时间轴可验证
```

它不等价于该被试已经通过最终科学 QC。因此正式 manifest 将：

```text
qc_pass = null
```

保留到 downstream QC 阶段。这样可以避免因为某个暂定 QC 阈值而提前删除昂贵模型已经提取出的信息。

## 14. 当前方法的报告级概括

可在报告中概括为：

> 本研究对正式实验 baseline 开始至第二任务区块结束的 RGB 视频进行连续多模态视觉分析。整体采用 raw-first 策略：以原视频完整帧率计算基于 OpenCV 相邻灰度帧差的全局运动量；以 10 Hz 使用 MediaPipe Pose Landmarker 提取 33 点人体姿态信息；以 15 Hz 使用 Py-Feat 2.1.1 Detectorv2 scientific core 提取面部动作单元、情绪、注视、头部姿态及 478 点 FaceMesh。AMD 工作站通过 ONNX Runtime DirectML 执行由 Py-Feat 模型导出的 RetinaFace 与多任务 scientific core，NVIDIA 工作站使用原生 PyTorch/CUDA Detectorv2；两端保持相同采样频率、模型语义与检测阈值，并通过代表帧 parity 验证跨后端可比性。模型推理阶段完整保留帧位置、采集帧号、Unix 时间戳、行为上下文、多脸/no-face 状态及模型原始输出；EAR、眨眼、PERCLOS、tracking、姿态运动和各类时间窗统计均在下游从 raw 数据重建，以避免早期筛选造成不可逆信息损失。
