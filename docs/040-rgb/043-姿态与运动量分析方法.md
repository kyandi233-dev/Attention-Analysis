# 043｜姿态与运动量分析方法

## 1. 为什么 Pose 与 Motion 要分开

RGB 身体分析同时回答两个问题：**身体具体怎么动**由 Pose 关键点回答；**总体动了多少**由 Motion Energy 回答。两者互补，不是二选一。

## 2. MediaPipe Pose

当前采用 MediaPipe Tasks Pose Landmarker / Pose Lite / `VIDEO` 模式。正式 RGB 机位主要记录坐姿被试的上半身，因此正式研究变量以头、肩、肘、腕和可见时的髋部为主；长期位于画面外的膝、踝、脚 landmark 不直接解释为可靠观测。

### 10 fps 决策

`sub-031` 首次完整正式时间窗 pilot 使用 10 fps：15,494 个采样时点全部检测到 pose，处理约 429.1 s（约 7.15 min），实际约 36.1 inference/s，输出约 22.7 MB。该速度已满足当前时间预算，因此撤销此前临时 5 fps 方案，恢复并保留 **10 fps**。跳过的非采样帧仍只 `grab` 推进 AVI，采样帧才 `retrieve/decode`。

### Raw 信息保留

第一次推理完整保存每个返回人体的 33 个 normalized landmarks 与 33 个 world landmarks，包括 `x/y/z`、visibility、presence，以及 pose bbox、frame/timestamp identity、phase/block/trial/probe。Raw 层允许最多 2 pose；检测失败采样帧仍保留 `pose_valid=False`。不请求 segmentation mask。

### 上半身 landmark QC

不能用全部 33 个 landmark 的 grand mean 判断质量，因为下肢长期出画会系统性拉低 mean visibility/presence。新增：

```powershell
python scripts/rgb_analysis.py --stage pose-qc --subject sub-031
```

它只读取已有 `_test/sub-031_pose-test.parquet`，不重新跑 MediaPipe，输出 `_test/sub-031_pose-qc.json`。重点逐项检查：

- `left/right_shoulder`；
- `left/right_elbow`；
- `left/right_wrist`；
- `nose`；
- `left/right_hip` 作为 optional trunk landmarks。

每个 landmark 记录 frame coverage、visibility/presence 分位数、≥0.5/≥0.8 比例、是否位于画内，以及 world coordinate availability。肩/肘/腕是主要上半身质量依据；髋部若质量差不自动否定 Pose，而是改用 shoulder width 做尺度标准化。

### Pose-derived upper-body motion

`body_motion` 这一简称容易和像素级 `body_motion_energy` 混淆，因此正式区分：

1. **Pose-derived upper-body motion**：直接由已有 landmarks 的位置变化计算，不再读视频；
2. **body_motion_energy**：只在被试人体 ROI 内做像素帧差，需要重新消费 RGB 帧，留到正式统一视频读取时计算。

现阶段新增：

```powershell
python scripts/rgb_analysis.py --stage pose-features --subject sub-031
```

输出 `_test/sub-031_pose-features-test.parquet`。逐个 Pose 时点派生：

- left/right/mean wrist motion；
- left/right/mean elbow motion；
- left/right/mean shoulder motion；
- `upper_body_motion_swidth_per_sec`；
- shoulder center / shoulder width；
- hip center（若可用）；
- `trunk_angle_deg_from_vertical`（若髋部可用）；
- 每帧上半身 visibility/presence QC。

运动速度统一按真实 `dt_ms` 计算，并用 shoulder width 做尺度标准化，单位可解释为“每秒移动多少个肩宽”。Raw landmarks 保留不变，派生特征可随时重算。

如果某帧出现多个 pose，当前派生层先标记 `primary_pose_ambiguous=True`，不在未冻结 primary-subject 规则前强行把第 0 个 pose 当被试。

## 3. Motion Energy

第一版使用 OpenCV 相邻灰度帧差异：

```text
mean_abs_difference = mean(abs(gray_t - gray_t-1))
global_motion_energy = mean_abs_difference / 255
global_motion_energy_per_sec = global_motion_energy / dt_seconds
```

真实 Unix timestamp gap 或 capture-frame 缺号时，gap 后第一帧保留身份信息，但相邻帧 Motion 写 missing。`sub-031` 已验证 102 ms、101 ms、13.853 s、758 ms 四个 timestamp gap 均正确处理。

人工 representative-frame review 已确认 baseline 最高 global Motion 主要由主试进入/离开画面造成。因此 `global_motion_energy` 保留为整画面变化量/QC，不直接等价于被试身体运动。

`body_motion_energy` 最终会在人体 ROI 内计算，作为更接近被试自身总体像素运动量的候选指标；为避免现在再次独立扫描大体积 AVI，它等待 Face backend 冻结后与 Motion/Pose/Face 的正式单次视频读取一起实现。

## 4. 性能与正式 batch 策略

`sub-031`：global Motion 约 78.3 fps；Pose 10 fps 完整分析约 7.15 min。正式 batch 不应让 Motion、Pose、Face 各自完整解码大体积 AVI 一遍。三个 backend 验证完成后优先统一视频读取：Motion 消费全帧，Pose 消费 10 fps 采样帧，Face 按冻结后的 fps/batch 消费相应帧，同时计算人体 ROI 的 `body_motion_energy`。

## 5. 与 Face 的关系

Face benchmark 与 Pose-derived feature 开发在工程上独立。Pose QC/pose-features 只读取已经生成的 Parquet，耗时很低，因此无需等它们全部“正式冻结”才开始 Face。当前最快路线是：本地立即跑 pose-qc / pose-features，同时下一开发步骤进入 Py-Feat vs LibreFace benchmark。
