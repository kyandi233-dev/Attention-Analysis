# 043｜姿态与运动量分析方法

## 1. 为什么 Pose 与 Motion 要分开

RGB 身体分析同时回答两个问题：**身体具体怎么动**由 Pose 关键点回答；**总体动了多少**由 Motion Energy 回答。两者互补，不是二选一。

## 2. MediaPipe Pose

当前采用 MediaPipe Tasks Pose Landmarker / Pose Lite / `VIDEO` 模式。正式 RGB 机位主要记录坐姿被试的头肩区域，因此正式研究变量必须依据真实可见范围决定，而不能因为 MediaPipe 总能返回 33 个点，就把画外肘、腕、髋、下肢的外推坐标当作真实观测。

### 10 fps 决策

`sub-031` 首次完整正式时间窗 pilot 使用 10 fps：15,494 个采样时点全部检测到 pose，处理约 429.1 s（约 7.15 min），实际约 36.1 inference/s，输出约 22.7 MB。该速度满足当前时间预算，因此保留 **10 fps**。跳过的非采样帧只 `grab` 推进 AVI，采样帧才 `retrieve/decode`。

### Raw 信息保留

第一次推理完整保存每个返回人体的 33 个 normalized landmarks 与 33 个 world landmarks，包括 `x/y/z`、visibility、presence，以及 pose bbox、frame/timestamp identity、phase/block/trial/probe。Raw 层允许最多 2 pose；检测失败采样帧仍保留 `pose_valid=False`。不请求 segmentation mask。

Raw 层不因某个 landmark 当前不可见而删除它：其他被试可能机位更宽，完整输出仍保留以后重新判断的可能性。

### 上半身 landmark QC：sub-031 实测

`pose-qc` 只读取已有 `_test/sub-031_pose-test.parquet`，不重新跑 MediaPipe：

```powershell
python scripts/rgb_analysis.py --stage pose-qc --subject sub-031
```

`sub-031` 的结果显示，“15,494/15,494 帧都有 pose”只说明人体检测持续成功，不等于所有 33 个 landmark 都可用。真正按 landmark 检查后：

- `nose`：visibility≈0.999、presence≈0.998、100% in-frame，质量极高；
- `left/right shoulder`：visibility≈0.995/0.996，presence≈0.956/0.979，100% in-frame，质量极高；
- `left elbow`：mean visibility≈0.395、presence≈0.060、in-frame≈0；
- `right elbow`：mean visibility≈0.620，但 presence≈0.089、in-frame≈0；
- `left/right wrist`：mean presence≈0.006/0.015、in-frame≈0，基本属于画外外推；
- `left/right hip`：mean presence≈0.0007/0.0009、in-frame=0，完全不应作为真实躯干观测。

因此 `world_coordinate_fraction=1.0` 不能解释成“这些画外 landmark 很可靠”；MediaPipe 即使对画外部位也会返回模型估计的 world coordinates。正式派生特征必须同时检查 in-frame、visibility 与 presence。

### Pose-derived feature 的质量门控

`pose-features` 从 v0.2 起不再直接使用所有模型坐标。Raw landmark 仍完整保留，但一个 landmark 只有同时满足下列开发条件才可参与运动计算：

```text
visibility >= 0.5
presence   >= 0.5
x/y 位于图像范围 [0, 1]
```

这些是**派生层开发阈值，不是 raw 删除阈值，也尚未冻结为最终科学 QC 标准**。Pose 当前为 10 fps，正常相邻采样约 100 ms；派生速度若 `dt_ms > 300 ms` 则触发 `pose_timestamp_gap`，当前帧保留但不跨 gap 计算运动。

`sub-031` 修正版 `rgb-pose-features-v0.2` 实测：

- 总 Pose 时点：15,494；
- multi-pose ambiguous：0；
- `gap_reset_rows=2`，对应 10 fps 采样层真正超过 300 ms 的两次长断流；
- `shoulder_motion_valid_rows=15,491`，即除首帧和两个 gap reset 外几乎全程有效；
- `elbow_motion_valid_rows=0`；
- `wrist_motion_valid_rows=6`；
- `trunk_angle_valid_rows=0`；
- `upper_body_motion_valid_rows=15,491`。

因此对当前正式机位，**Pose 的稳定研究价值主要来自双肩，而不是完整上半身骨架**。`upper_body_motion_swidth_per_sec` 在 `sub-031` 中事实上几乎完全由双肩构成，不能宽泛解释为“整个上半身总运动”；正式分析应优先报告/使用明确命名的 `shoulder_motion_swidth_per_sec`、shoulder center 和 shoulder-line posture 指标。腕、肘、髋相关字段继续保留为 opportunistic 输出：仅当某个被试实际进入画面且质量门控通过时使用。

新增输出还记录每个关键点的 `*_quality_valid`、`gap_before/gap_reason`、`upper_body_motion_landmark_count` 与 `arm_motion_landmark_count`，以避免聚合变量在不同时间点由不同 landmark 组成却被静默解释成同一含义。

### Pose-derived motion 与 body_motion_energy

两个概念正式区分：

1. **Pose-derived shoulder/body posture motion**：由质量合格的 landmark 位置变化计算，不再读视频；当前机位以 shoulder motion 为主；
2. **body_motion_energy**：只在被试人体 ROI 内做像素帧差，需要重新消费 RGB 帧，留到正式统一视频读取时计算。

现阶段运行：

```powershell
python scripts/rgb_analysis.py --stage pose-features --subject sub-031
```

输出 `_test/sub-031_pose-features-test.parquet`。运动速度按真实 `dt_ms` 计算，并用可靠 shoulder width 做尺度标准化，单位为“每秒移动多少个肩宽”。

如果某帧出现多个 pose，派生层标记 `primary_pose_ambiguous=True`，不在未冻结 primary-subject 规则前强行把第 0 个 pose 当被试。

## 3. Motion Energy

第一版使用 OpenCV 相邻灰度帧差异：

```text
mean_abs_difference = mean(abs(gray_t - gray_t-1))
global_motion_energy = mean_abs_difference / 255
global_motion_energy_per_sec = global_motion_energy / dt_seconds
```

真实 Unix timestamp gap 或 capture-frame 缺号时，gap 后第一帧保留身份信息，但相邻帧 Motion 写 missing。`sub-031` 已验证 102 ms、101 ms、13.853 s、758 ms 四个 timestamp gap 均正确处理。

人工 representative-frame review 已确认 baseline 最高 global Motion 主要由主试进入/离开画面造成。因此 `global_motion_energy` 保留为整画面变化量/QC，不直接等价于被试身体运动。

`body_motion_energy` 最终会在人体 ROI 内计算，作为更接近被试自身总体像素运动量的候选指标；为避免现在再次独立扫描大体积 AVI，它等待 Face backend 冻结后与 Motion/Pose/Face 的正式单次视频读取一起实现。

## 4. 性能与正式 batch 策略

`sub-031`：global Motion 约 78.3 fps；Pose 10 fps 完整分析约 7.15 min。正式 batch 不应让 Motion、Pose、Face 各自完整解码大体积 AVI 一遍。三个 backend 验证完成后优先统一视频读取：Motion 消费全帧，Pose 消费 10 fps 采样帧，Face 按冻结后的 fps/batch 消费相应帧，同时计算人体 ROI 的 `body_motion_energy`。

## 5. 与 Face 的关系

Pose representative pilot、landmark QC 和质量门控后的派生 feature 已完成首个正式视频验证。**不再等待更多 Pose 开发才开始 Face**；下一开发步骤直接进入 Py-Feat vs LibreFace benchmark。Pose 在后续 representative subjects 上只需检查肩部质量是否复现，并保留腕/肘/髋作为可选而非必需测量。
