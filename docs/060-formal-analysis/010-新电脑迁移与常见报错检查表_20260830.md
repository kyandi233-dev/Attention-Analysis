# 新电脑迁移与常见报错检查表｜2026-08-30

本文件是 `ANALYSIS_SETUP_FIRST.md` 的执行型检查表。目标不是重新讲科学方法，而是在换电脑、换硬盘、换 Conda 安装位置或新建终端后，尽量把路径、环境、接口和数据可用性问题提前暴露。

## 1. 开机/新终端后先做的 10 项检查

```powershell
cd "<Attention-Analysis 仓库>"

python -c "from attention_pipeline.path_registry import load_path_registry; r=load_path_registry(); print(r.path); print(r.data.get('version')); print(r.digest)"
```

预期：分支正确、pull 为 fast-forward/已最新、Conda 可调用、`paths.local.yaml` 存在、path registry version 为 1/2/3（新电脑推荐 3）。

## 3. 路径注册表逐键检查

新电脑不要先改 science config。先核对 `configs/paths.local.yaml`。推荐最少确认：

```text
formal_raw_roots
cohort_manifest
repeat_registry
questionnaire_derived_data
behavior_output_root
nir_analysis_ready_source_manifest_json
nir_analysis_ready_root
nir_analysis_tables_root
stimulus_visual_properties
rgb_raw_output_root
rgb_analysis_ready_root
rgb_analysis_tables_root
```

其中最常见问题是：

- 盘符变了；
- 外接硬盘没有挂载；
- 复制了旧电脑 `paths.local.yaml`；
- `${ENV_VAR}` 变量只在旧电脑配置过；
- Windows 文件夹改名或多套数据目录并存；
- 输出目录指向只读/同步盘；
- staged NIR JSON manifest 与 legacy NIR CSV manifest 写反。

## 4. NIR 特别检查

### 4.1 source manifest 格式

当前权威：

```text
nir_analysis_ready_source_manifest_json
  -> JSON object
  -> sessions[]
```

历史 adapter：

```text
nir_source_manifest
  -> CSV
  -> 仅 legacy nir-adapt
```

看到 `JSONDecodeError`、`source manifest root must be an object`、`sessions must be a non-empty list` 时，第一检查这两个路径是否串线。

### 4.2 session availability

如果出现：

```text
requested sessions absent from source manifest
```

含义是“请求的 session 没有被当前 NIR source manifest 声明为可用”，不是 participant 不存在。先检查：

1. 该场是否实际录到/完成 NIR producer；
2. manifest 是否漏登记；
3. session ID 格式是否一致；
4. 是否误把 Behavior 的全 cohort 当成 NIR source availability list。

不要创建空 NIR 行去凑 44 场，也不要填 0。

### 4.3 OAR/PIR 语义

看到历史字段 `pir_oar_allowed` / `pir_oar_refused` 时，应先确认是不是 legacy 资产。当前正式语义只有：

```text
PIR/iris geometry: refused
ocular-aperture ratio: retained as eye-opening QC candidate
ocular-aperture formal endpoint: false
```

OAR 不能直接叫 EAR、blink 或 PERCLOS。

## 5. RGB 特别检查

### 5.1 整场没有 RGB

如果某 known session 没有 RGB subject directory，当前 runner 应把它记录为：

```text
rgb_source_absent
motion = not_estimable
pose = not_estimable
blink = not_estimable
```

这是合法 modality missing，不是 participant identity failure。不要因此改 cohort manifest，也不要删除 Behavior/NIR/mmWave 中对应 session。

### 5.2 只有部分 producer 文件

目录存在但缺：

- `*_motion_raw.parquet`
- pose landmarks parquet
- face raw parquet

时，只影响对应 component。Motion 已成功时，Pose/Blink 缺失不应把 Motion 结果作废。

### 5.3 Parquet 报错

常见检查：

```powershell
python -c "import pyarrow; print(pyarrow.__version__)"
python -m pip show pyarrow
```

如果包存在但文件仍打不开，再检查文件是否为 0 byte、传输中断、同步软件占用或 schema 与当前 producer 版本不一致。

## 6. mmWave 特别检查

mmWave 正式处理不在本仓库。新电脑迁移时要避免两个错误：

1. 把结构性无效文件当成“数值为 0”；
2. 因为 mmWave 只有部分场次可加载，就把其他模态 cohort 一起缩小。

正确做法是保留 governed session list，然后在 mmWave availability/QC 中记录每场状态。只有显式做 paired multimodal comparison 时，才建立 common-available subset，并报告这个 subset 的 session/participant 分母。

## 7. Behavior/身份表检查

如果出现 join/identity conflict：

- 先确认 `cohort_manifest`、`repeat_registry`、`questionnaire_derived_data` 是否来自同一轮数据整理；
- 检查 `session_id` 是否唯一；
- 检查 participant_key 与 repeat mapping 是否冲突；
- 不从 `sub-XXX` 数字大小推 participant；
- 不因 RGB/mmWave 缺失修改 participant mapping。

现实中的 modality missing 与 participant identity 是正交问题，不要用一个问题去“修”另一个问题。

## 8. Windows 常见运行问题

| 现象 | 处理 |
|---|---|
| `WinError 32` / PermissionError | 关闭 Excel、VSCode preview、正在读写同一 CSV/Parquet 的 Python，检查杀毒/同步软件锁文件 |
| 路径过长 | 尽量把 clone/output 放到较短父目录；不要把 science config 改成硬编码补丁 |
| 中文路径第三方工具失败 | Python/pandas 通常可用；若外部 executable 不支持，优先调整机器路径注册表，不改科学口径 |
| 空间不足 | NIR/RGB 派生前检查输出盘剩余空间；正式产物不写回 Git 仓库 |
| `git pull --ff-only` 失败 | `git status` 查本地改动；不要 force/reset 覆盖并行工作 |
| Conda env 名重复但位置不同 | `conda env list` + `where.exe python` 核对实际 executable |
| `pip` 装到 base | 始终用 `python -m pip`，并先 `where.exe python` |

## 9. representative smoke 前检查

不要一配置好新电脑就直接全量。建议顺序：

```text
portable pytest
-> path registry load
-> one known available Behavior session
-> one known available NIR session
-> one known available RGB session
-> one known missing-modality session（验证不会删 cohort / 误触发 producer）
-> inspect manifests + failure/QC tables
-> 再决定全量
```

特别推荐故意选一个“某模态缺失但 participant/session 已知”的场次做 smoke，因为它能直接验证 availability contract 是否按预期工作。

## 10. 哪些现象不是代码错误

以下情况本身不应自动判为 pipeline failure：

- RGB 不是 44/44；
- mmWave 不是 44/44；
- 某个 RGB component 不可估计；
- 某场 NIR 未在 NIR source manifest；
- questionnaire 某场缺回答（只要 cohort/identity 规则允许）；
- legacy tests 因缺旧本机原始数据而明确 skip。

真正需要警惕的是：这些缺失是否被静默填 0、静默删 session、错误改变 participant ID、自动重跑昂贵 producer、或者没有写进 availability/QC/failure manifest。

## 11. 最后确认输出位置

正式结果应写在仓库外。本机只通过 path registry 指定：

```text
behavior_output_root
nir_analysis_ready_root
nir_analysis_tables_root
rgb_analysis_ready_root
rgb_analysis_tables_root
mmwave_output_root（如本机只做跨模态索引/未来接入）
```

如果输出意外出现在 Git 仓库的 source/config/docs 目录，立即停止检查配置。当前正式下游不应覆盖原始 producer 数据，也不应把大体积正式结果纳入 Git。
