# 013｜仓库资产与复现关系

> 2026-08-24（Asia/Shanghai）｜当前资产关系以 `nvidia-cuda` 为维护分支；退出路线通过工作记录、决策记录和 tags 追溯。

仓库一级目录按“当前职责”分类，而不是按“历史上曾经参与过什么过程”分类。同一个实体只保留一个 canonical role；已经退出当前工作的资产通过工作记录、decision record、Git 历史和明确冻结的历史实现追溯，不在 `nvidia-cuda` 中无意义重复堆放。

## 核心数据流

```text
datasets/
    ↓ 训练数据与固定划分
training/
    ↓ 训练过程与训练结果
model weights
    ↓ 冻结到正式运行环境
runtime/
    ↓ 正式分析
仓库外正式全量输出
```

## 当前一级目录职责

| 目录 | 回答的问题 | 典型内容 |
|---|---|---|
| `src/attention_pipeline/` | 系统核心逻辑怎么实现？ | 当前 BB 行为源码、历史 BBB 独立复现源码及其他保留的可复用 Python 逻辑 |
| `scripts/` | 当前还需要执行哪些仓库级任务？ | 数据集抽取、模型评估、当前 BB 行为入口、明确标记的历史 BBB 重跑入口 |
| `configs/` | 仓库级配置是什么？ | 当前 BB 行为配置、历史 BBB 可执行配置、预实验/兼容配置；正式 NIR 以 runtime 内配置为准 |
| `datasets/` | 训练数据从哪里来？ | 冻结标注数据与 provenance |
| `training/` | YOLO 模型怎么训练出来？ | split、dataset yaml、runs、训练结果 |
| `runtime/nir-formal/` | 怎样复现已经运行过的正式 NIR？ | 冻结权重、RITnet 运行源码、运行脚本、依赖与正式配置 |
| `runtime/legacy/` | 怎样追溯旧环境？ | 历史运行快照；不属于 current runtime 依赖 |
| `tests/` | 怎样自动检查仓库级代码没有坏？ | current Behavior、共享 IO、NIR/历史兼容逻辑等回归测试 |
| `docs/` | 当前方法、模块状态、决策和历史过程在哪里解释？ | overview、模态文档、decisions、工作记录 |

## 为什么没有根 `models/` 和 `artifacts/`

当前正式模型已经有明确 canonical 位置：

```text
training/nir-eye-yolo/.../best.pt
runtime/nir-formal/models/nir-eye-yolo26n-best.pt
runtime/nir-formal/models/ritnet-best_model.pkl
runtime/nir-formal/ritnet/
```

根 `models/` 原先保存的第三方完整源码副本与历史候选模型均不参与当前正式运行，已在记录来源、用途和淘汰原因后从 `nvidia-cuda` 删除。根 `artifacts/` 原先保存的 Gate/preview/ROI compare/smoke 等阶段性输出也已按用户授权全部删除。它们不是当前正式结果的 provenance 主链，历史用途和删除原因由工作记录与 Git 历史保留。

因此当前主线不再创建空壳 `models/README.md` 或 `artifacts/README.md` 来说明已经不存在的目录；对应说明统一放在 `docs/`。


两套实现的统计逻辑不能混用。当前正式结果只认 BB；历史 BBB 保留 B1/B2/B3、sub-011~030 等当时口径。

## 正式原始数据根

正式原始数据在物理上分布于两块外接存储设备，在逻辑上只有两个目录：`正式实验` 与 `Data`。Windows 对两块盘的盘符分配可能随连接顺序在 `E:` 与 `F:` 之间交换，所以 current config 不把某一逻辑目录绑定到固定盘符，而是声明四个候选路径：

```text
E:/正式实验
F:/正式实验
E:/Data
F:/Data
```

Behavior 与 NIR 在运行时忽略不存在的候选根，并在所有有效根中发现 `sub-XXX_` 数据。若同一被试在多个有效根中出现重复正式数据，程序不得静默选择其中一份，而应中止并报告重复位置。

这四个候选路径表达的是“两种逻辑目录 × 两种可能盘符”，不是四份正式数据，也不是四个固定存储根。
