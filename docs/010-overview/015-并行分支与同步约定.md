# 015｜并行分支与同步约定

> 2026-08-26｜本文件描述当前仓库的并行工作方式。它是当前状态说明，不改写 `docs/工作记录/` 中的历史记录。

## 1. 分支不是不同项目

`Attention-Analysis` 只有一个项目。当前拆出多条 branch，主要目的是让 NIR、Behavior、RGB、不同硬件上的开发可以并行推进，降低同一时间修改相同文件造成冲突的概率。

因此：

- `rgb-amd` 不是“只允许放 RGB 文件”的子仓库；
- `rgb-nvidia` 也不是独立项目；
- 已经成熟的 NIR、Behavior、共享配置、共享 docs 可以同步到 RGB 工作线；
- RGB 工作线中的成熟改动最终也会回并综合主线；
- 最终目标仍是形成统一的 Attention-Analysis 仓库状态。

## 2. 当前分支职责

| 分支 | 当前职责 | 说明 |
|---|---|---|
| `amd-DirectML` | AMD 综合线 | 可同时包含 NIR + Behavior + NIR-Behavior + RGB；保存 AMD 已成熟的综合状态 |
| `rgb-amd` | 当前 AMD RGB 工作线 | 当前 RGB 正式化主要在这里继续；允许同步 AMD 综合线中的 NIR/Behavior/共享文档与代码 |
| `rgb-nvidia` | 当前 NVIDIA RGB 工作线 | 用于 NVIDIA RGB/CUDA 的独立开发，避免直接干扰正在使用的 NVIDIA 综合线 |
| `nvidia-cuda` | NVIDIA 综合线 | 当前有人在实际使用；本轮文档同步不直接修改该分支 |
| `analysis/multimodal-integration` | 多模态整合工作线 | 用于 NIR / Behavior / RGB 等结果层面的进一步整合 |

已经退出当前开发流的旧分支包括 `rgb-dev`、`rgb-nvidia-cuda`、`analysis/nir-behavior-v2`。历史过程仍由 Git history、tags 和 `docs/工作记录/` 保留。

## 3. 同步原则

### 3.1 当前说明文档要同步

当科学定义、正式入口、输出结构或分支职责发生变化时，应同步检查：

- 根 `README.md`；
- 对应模态的 `docs/.../README.md`；
- 环境/运行说明；
- `scripts/README.md`；
- 当前有效的 architecture / decisions / methods 文档。

### 3.2 历史记录不追溯改写

`docs/工作记录/`、历史快照、旧 benchmark 结论按当时状态保留。即使其中出现 `rgb-dev`、旧 backend 候选或“待完成”等文字，也不代表当前仍是该状态。

### 3.3 硬件相关命令保持分支差异

共享的是科学定义、schema、行为对齐逻辑和信息保留原则；硬件执行层可以不同：

```text
AMD Face:    Py-Feat scientific core → ONNX Runtime DirectML
NVIDIA Face: Py-Feat scientific core → native PyTorch CUDA
```

因此不能为了“文档完全一样”而覆盖硬件特定路径、Conda 环境、provider、batch 或本机数据根。

### 3.4 不直接把整条分支强行覆盖另一条

并行分支可能各自包含有效的新提交。同步时优先按模块/文件审计差异；需要 merge 时再单独解决冲突，不使用 force push 作为常规同步手段。

## 4. 当前 RGB 接力关系

当前 AMD RGB 正式化继续在：

```text
rgb-amd
```

`amd-DirectML` 中已经完成的 Py-Feat DirectML 验证、15 Hz 定义、raw schema、tracking/eyelid 规则、Motion/Pose 科学层都可以作为 `rgb-amd` 的上游成熟资产。后续 `rgb-amd` 跑通正式单被试和批处理后，再同步/回并综合线。

NVIDIA RGB 则在：

```text
rgb-nvidia
```

继续 CUDA-specific 验证。由于 `nvidia-cuda` 当前有人在使用，本轮同步只更新 `rgb-nvidia`，不直接改 `nvidia-cuda`。
