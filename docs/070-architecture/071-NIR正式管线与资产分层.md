# 071｜NIR 正式管线与资产分层

## 为什么需要单独说明架构

当前仓库经历了多轮研究迭代，不能再用“一个 `src/` + 一个 CLI”概括全部结构。早期 NIR review、六算法 benchmark、连续序列实验、自训练 YOLO、portable GPU package 和最终全量处理属于不同阶段。如果不区分代码层、训练资产层、runtime 层与大体量输出层，很容易把历史入口误认为当前主链，或者把 portable 默认配置误写成最终 full-run 参数。

当前合理的整体结构是：

```text
原始正式数据
    ↓
训练数据资产 ──→ YOLO26n 训练 / test
    ↓                    ↓
正式 NIR 视频       frozen best.pt
    │                    │
    └────────────┬───────┘
                 ↓
        YOLO + tracking + RITnet runtime
                 ↓
        逐帧 / 逐眼测量与 QC
                 ↓
        大体量正式输出（数据盘）
                 ↓
        轻量 provenance / 文档（Git）
```

## 第一层：原始数据与训练数据

原始正式视频不直接存入代码仓库。眼框模型使用的冻结数据集位于：

```text
datasets/nir-eye-dataset-v1/
```

该目录负责保存源图片、YOLO 标注和 batch provenance。派生训练工作区位于：

```text
yolotrain/
```

其中按被试级固定 train / val / test，并保存 Ultralytics run、validation 记录与 `best.pt`。

这两个目录的区别是：`datasets/` 是训练源数据资产，`yolotrain/` 是派生训练工作区；不应把二者看作两份独立原始数据集。

## 第二层：可复用源码与历史研究代码

```text
src/attention_pipeline/
```

保存项目可复用 Python 逻辑，但它本身由多个研究阶段逐步形成。当前主要包括：

- `behavior/`：早期行为 evidence / compatibility 层；
- `behavior_formal/`：正式 BBB SART 分析层；
- `nir/`：ROI 几何、正式时间轴以及历史 review / benchmark / sequence 代码；
- `config.py`、`protocol.py`、`validation.py` 等共享基础逻辑。

旧 `cli.py` 仍直接连接早期 behavior 与 NIR review/benchmark/sequence，因此不能仅因为它叫统一 CLI 就自动视为后来 YOLO + tracking + RITnet 全量入口。

## 第三层：可运行脚本

```text
scripts/
```

主要保存：

- 训练数据构建；
- YOLO test 评价；
- 历史 ROI 后端比较；
- PuRe/PuReST、DeepVOG、Iris 等适配/诊断；
- 一次性研究与复核入口。

`scripts/` 不应再建设第二套核心算法库。历史脚本继续留在原路径，是为了保持工作记录、artifact 和命令引用的可复现性。

## 第四层：frozen portable runtime

当前仓库已经核验到完整 YOLO26n + tracking + RITnet 端到端实现位于：

```text
runtime/nir-yolo-tracking-ritnet-v1/
```

核心入口：

```text
run_pipeline.py
```

运行包包含：

```text
config.yaml
run_pipeline.py
ritnet_runtime.py
models/nir-eye-yolo26n-best.pt
models/ritnet-best_model.pkl
ritnet/densenet.py
requirements.txt
SHA256SUMS.txt
```

外层同时保存同名 ZIP 和 ZIP SHA256。因为 package 内部已有 `SHA256SUMS.txt`，且 ZIP 是 2026-08-22 的冻结迁移资产，所以整理仓库时不应直接修改 package 内 README/config 来追赶当前项目文字，否则会破坏 frozen package 与 checksum 的一致性。当前状态说明放在 `runtime/README.md`。

## 模型身份

portable runtime 内的 YOLO 权重与训练产物：

```text
yolotrain/runs/yolo26n_eye_100epoch/weights/best.pt
```

为同一个 Git blob。portable runtime 内的 RITnet 权重与：

```text
models/RITnet-master/best_model.pkl
```

也为同一个 Git blob。

因此 runtime 是正式模型的可移植运行封装，不是另一个独立训练版本。

## 第五层：运行输出

portable runtime 的代码会产生：

```text
frames.csv
eyes.csv
summary.json
run_manifest.json
overlays/
rois/  # 仅开启保存时
```

其中 `frames.csv` 负责逐帧记录 YOLO/tracker 来源、重检测原因、检测数量、状态与耗时；`eyes.csv` 负责逐帧×眼记录 bbox、ROI、RITnet 椭圆、confidence 和状态；`summary.json` 汇总处理速度与状态计数；`run_manifest.json` 记录命令、环境、配置和模型 SHA256。

对于一百多名、每人约 25 分钟的视频，大体量 CSV、overlay 和中间 ROI 不适合直接纳入 Git，继续保留在分析数据盘是合理的。但 `run_manifest.json` 或等价参数摘要体积很小，具有关键复现价值。

## 当前 provenance 缺口

当前项目事实是正式 NIR 全量已经完成，但当前 Git 分支没有保存最终 full-run 的 `run_manifest.json` 或全量输出目录，也没有 2026-08-22 之后的 committed NIR 工作记录。因此当前能确认：

- 全量已经运行；
- 完整 YOLO + tracking + RITnet 实现在哪里；
- 使用的 YOLO/RITnet 模型血缘；
- portable runtime 能输出哪些 provenance。

当前不能仅靠 package 默认配置确认：

- 最终 tracker；
- 最终 redetect interval；
- 最终 ROI expansion；
- 最终 RITnet 门控；
- 最终设备/环境；
- 最终输出字段是否在全量运行前又做过修改。

因此下一次能访问实际全量输出电脑时，最优先寻找的不是大体量结果复制，而是 `run_manifest.json`、`summary.json`、运行命令或等价参数记录。

## 架构整理原则

1. `src` 保存可复用逻辑和已有历史核心，不为了形式统一强行吸收 frozen runtime。
2. `scripts` 保持运行入口/研究工具角色，不重复维护核心算法。
3. frozen runtime 作为可移植研究资产整体保留，并通过外层 README 解释其历史状态。
4. 原始视频和全量大结果继续与 Git 分离。
5. 关键轻量 provenance 应在找到原始证据后补回仓库。
6. 历史候选代码不因正式路线确定而删除；若未来需要删除，单独确认。
